# Platform administration: two accounts, password + emailed login code

## Selected design (2026-10-03)

The user chose no WireGuard, no Cloudflare Zero Trust and no Google Authenticator. Two email addresses supplied privately by the user are the only permitted management identities. The source repository contains no actual account passwords or personal address allowlist. Those are operator-provisioned private files. No subscription was activated. The previous VPN/Cloudflare/TOTP service implementations and templates were removed; the old generated migration is retained only as schema history, followed by a migration removing its TOTP fields.

This is a password plus email-code flow. Email is NOT a phishing-resistant authenticator and must not be described as providing NIST AAL2 assurance. Its security depends on the recipient mailbox. The known limitation is accepted by the user's explicit choice, not silently described as an upgrade over TOTP.

## Login and session enforcement

- Only `https://yonetim.schoolasist.com` hosts management requests. Backend checks the trusted resolved Host and HTTPS on start, code verification, JWT use and refresh; public school hosts cannot be used as a second management login route. Proxy forwarding remains limited to trusted loopback, one hop, with For/Host/Proto overwritten together. Hostname is routing isolation, not an authentication factor.
- `AdminAccess:Mode=EmailCode` and exactly two distinct valid `AdminAccess:AllowedEmails` are required. Missing, malformed or other modes fail closed. Config is server-only; changing a config value to the formerly used private modes does not create a bypass.
- Each account must be an active tenant-free Developer. Its Username and operator-bound PlatformAccessEmail must match an allowlisted address. No public registration, admin API, incoming header or code form can select an alternative code recipient. Allowlist enforcement continues on every admin request and refresh, so removing an address immediately blocks its old tokens.
- `/api/admin-auth/start` first validates the allowlisted account and its password through the existing hash/lockout mechanism. A successful password alone never grants JWT or refresh credentials. A random 6-digit code is sent only to that account through the existing TLS SMTP sender, never to both accounts or an arbitrary input recipient. No password is sent by email.
- Random 32-byte challenge token plus the code form a SHA-256 proof; only the token hash and proof hash are stored. The raw challenge token is not stored in the database, so the database alone does not supply enough information to enumerate the low-entropy code proof. No raw code, password or SMTP body is logged. The API returns only a challenge token, expiry and masked email hint.
- Challenge lifetime is 5 minutes, with at most 5 valid-format code attempts. Wrong code attempts also participate in a persisted per-user 15-minute failure limit. At most 3 code sends per account per 15 minutes and at least 60 seconds between requests; rejected SMTP delivery consumes the send budget. Optimistic user concurrency makes parallel start requests reserve at most one send. Limits and prior challenges survive process restart.
- A new challenge consumes its predecessors; replay and cross-account challenge/code combinations fail. Delivery success must be persisted before verification can succeed. SMTP failure, timeout, missing config or expired delivery grants no usable challenge or session. Verification atomically reserves an attempt, then uses user/challenge concurrency to consume successful codes once, including across API processes.
- Ordinary password login, PKCE issuance and legacy refresh cannot mint platform credentials. Sessions must have `admin_mfa` plus a database session binding and `AdminVerificationMethod=email`. Old TOTP or password-only sessions fail. The internal `admin_mfa` claim name is compatibility terminology, not an assertion of NIST assurance.
- Admin access tokens last at most 15 minutes. Sessions have server-enforced revocation, 15-minute idle timeout and an absolute 8-hour lifetime preserved through refresh rotation. User SecurityVersion changes invalidate tokens/challenges. Browser sessionStorage holds only the completed session; password clears after requesting a code, unconfirmed challenge state clears on reload/expiry. No remember-me or password persistence was added. Same-origin XSS remains a sessionStorage risk; preserve CSP and exclude third-party scripts from management pages.

## Private account provisioning files

`scripts/security/prepare-admin-email-access.py` generates exactly two distinct random 20-character passwords containing lower/upper/digit/symbol characters. It uses cryptographic randomness and creates a new output directory outside the repository with mode 0700; files have mode 0600. It never prints passwords, connects to a server or sends emails. It refuses duplicate/invalid email pairs and refuses an output directory within this repository. Do not regenerate over existing files accidentally.

Outputs:
- `yonetici-sifreleri.txt`: plaintext credentials for direct delivery to the user. This is a secret file, not suitable for Git, screenshots, email bodies, logs or shared links.
- `admin-email.env`: server-only allowlist/mode/host configuration.
- `provision-managers.sql`: contains only salted PBKDF2-SHA256 hashes (600,000 rounds, compatible with PasswordHasher.Verify). In a single transaction, it refuses collisions with school accounts, non-Developer accounts, duplicates or inactive accounts. It creates new tenant-free accounts or updates matching active platform accounts, increments versions, revokes their existing sessions and removes their pending challenges. It does not delete or elevate school users. Other Developer records may remain for audit/reference; policy denies their access because they are not the selected two accounts.

Run the generator with the two verified user-supplied addresses and a NEW private output directory. Actual addresses and credential paths are not embedded here. Protect the generated files and transfer server config/provisioning over the authorized encrypted deployment channel. Retain secrets only as needed; they must not become release artifacts.

## Production rollout (not performed)

1. Back up the database and existing release/configuration. Preserve the existing Data Protection directory outside releases for onboarding outbox encryption; MFA no longer uses it, but onboarding still does.
2. Review/apply all pending MFA migrations through the established deployment process. `ReplaceAdminTotpWithEmailCode` deliberately drops unused TOTP enrollment/recovery fields and adds email proof/delivery/send-history/session-method fields. Existing pending challenges lack a valid code proof/delivery stamp and cannot verify. Old management sessions lack `AdminVerificationMethod=email` and cannot refresh or authenticate.
3. Install the reviewed server-only `admin-email.env`; remove obsolete AdminAccess proxy keys/issuer/audience/peer config if present. Do not expose allowlist or SMTP passwords through NEXT_PUBLIC variables. Apply the private provisioning SQL with `ON_ERROR_STOP` after migrations; inspect only a non-secret row-count/role verification. The generated password file is not proof that production accounts have been updated.
4. Deploy the tested backend and static frontend through the existing release workflow. `deploy/nginx-admin-private.conf` now contains the dedicated HTTPS public management origin and clears all obsolete identity headers; its filename is retained for compatibility, not a private-network requirement. Obtain a valid certificate and renewal for the hostname, add its DNS record, test nginx, keep backend bound to 127.0.0.1:5206, and never bypass browser certificate warnings. Public website must not display a management login link.
5. Verify existing SMTP actually delivers a code to each intended address with that user's consented login, test one-use/expiry/failed code rejection, admin operations, logout, and normal school mobile/desktop login. Then return 404 for public-site `/admin` routes while preserving them on the management host. Code generation or UI fixtures do not establish mail deliverability.
6. Check time sync, HTTPS/HSTS/CSP, no-store/noindex responses, auth rate limits, secret-redacted logs, refresh rotation, account disabling and restart behavior. Do not weaken normal school tenant enforcement. No default/shared admin account is created.

## Recovery

No Authenticator enrollment or recovery-code route exists. If a user loses mailbox access, recovery is an audited operator intervention after identity verification; there is no public “skip code” or email-recipient change endpoint. Rotate the password with the existing hash format, increment SecurityVersion, revoke sessions/challenges, and update the server allowlist/binding only for the verified owner. Disabling the application account or removing its email from the pair revokes access.

## Validation

Backend security tests cover the exact pair, configuration failure, wrong role/binding/host/TLS, password failure without SMTP, matching-only recipient, proof storage, expiry, send budgets, delivery failure, cross-account mismatch, one-use codes, old login bypasses, revoked allowlist and session lifetime/revocation. All 60 focused backend tests passed. Frontend ESLint and production build passed (48 static pages, TypeScript checked). Browser UI verification used a loopback-only synthetic API: password-to-email-code transition, masked recipient, invalid-code rejection, and no VPN/Authenticator/recovery options. No actual personal passwords or recipient mailboxes were used in UI tests. Both generated passwords were verified as distinct 20-character values matching their salted hashes; private directory/file permissions were checked. Live provisioning, actual SMTP delivery, DNS/TLS and deployment remain unperformed.
